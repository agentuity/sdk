Use AI Gateway when framework server code should call supported model providers through Agentuity instead of requiring separate provider keys for local work. In v3, the documented path is `agentuity dev` environment wiring.

```bash
bun add openai
```

```typescript
import OpenAI from 'openai';

const openai = new OpenAI();

export async function summarize(message: string): Promise<string> {
  const response = await openai.responses.create({
    model: 'gpt-5.5',
    input: `Summarize this in one sentence:\n\n${message}`,
  });

  return response.output_text;
}
```

Run the app with `agentuity dev`. If `AGENTUITY_SDK_KEY` is available and you have not set your own OpenAI key, the CLI injects `OPENAI_API_KEY` and `OPENAI_BASE_URL` into the framework process before your app starts.

<Callout type="info" title="This page covers local v3 gateway wiring">
The examples here use `agentuity dev` and provider SDK env vars. Set your own provider key when you want direct provider traffic or when you have not verified gateway behavior in a deployed app yet.
</Callout>

## AI SDK

```bash
bun add ai @ai-sdk/openai
```

```typescript
import { generateText } from 'ai';
import { openai } from '@ai-sdk/openai';

export async function summarize(message: string): Promise<string> {
  const { text } = await generateText({
    model: openai('gpt-5.5'),
    prompt: `Summarize this in one sentence:\n\n${message}`,
  });

  return text;
}
```

AI SDK 6 accepts current and future OpenAI model IDs as strings. `@ai-sdk/openai` reads `OPENAI_API_KEY` and `OPENAI_BASE_URL`, so it works with the env vars injected by `agentuity dev`.

## Raw Anthropic SDK

```bash
bun add @anthropic-ai/sdk
```

```typescript
import Anthropic from '@anthropic-ai/sdk';

const anthropic = new Anthropic();

export async function classify(message: string): Promise<string> {
  const response = await anthropic.messages.create({
    model: 'claude-sonnet-4-6',
    max_tokens: 128,
    messages: [
      {
        role: 'user',
        content: `Classify the tone of this message:\n\n${message}`,
      },
    ],
  });

  return response.content.find((block) => block.type === 'text')?.text ?? '';
}
```

`@anthropic-ai/sdk` reads `ANTHROPIC_API_KEY` and `ANTHROPIC_BASE_URL`, so it works with the env vars injected by `agentuity dev`.

## When to Use AI Gateway

| Need | Use |
|------|-----|
| local framework development without separate provider keys | AI Gateway through `agentuity dev` |
| keep provider SDK code and let the CLI inject gateway config | AI Gateway |
| use a provider account, limits, or base URL directly | Set your own provider key and bypass the gateway |

## Local Development

`agentuity dev` looks for `AGENTUITY_SDK_KEY`, then wires supported provider env vars into the framework process before it loads your app code. Local env injection currently covers OpenAI, Anthropic, and Groq.

| Provider | API key env | Base URL env |
|----------|-------------|--------------|
| OpenAI | `OPENAI_API_KEY` | `OPENAI_BASE_URL` |
| Anthropic | `ANTHROPIC_API_KEY` | `ANTHROPIC_BASE_URL` |
| Groq | `GROQ_API_KEY` | `GROQ_BASE_URL` |

Start your app the same way you already do for v3 framework work:

```bash
agentuity dev
```

If the project SDK key is missing locally, the CLI tries to load it from project config and `.env`. When the project is not linked yet, the CLI can fall back to your authenticated CLI key for gateway routing and prints `agentuity project import`.

See [Running Local Development](/deploy-operate/local-development#ai-gateway-environment): how `agentuity dev` starts the framework server and loads Agentuity env values.

## Bring Your Own Provider Key

Set a provider key when you want the SDK to talk to that provider directly:

```bash title=".env"
AGENTUITY_SDK_KEY=sdk_your_project_key
OPENAI_API_KEY=sk-your-own-key
```

When `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, or `GROQ_API_KEY` contains your own provider key, `agentuity dev` leaves it in place. Use that path when you want provider-specific credentials or base URLs instead of Agentuity's gateway wiring.

## Explicit Provider Factories

Provider factories can still use AI Gateway locally when they read the provider env vars that `agentuity dev` injects.

```typescript
import { createOpenAI } from '@ai-sdk/openai';
import { generateText } from 'ai';

const openai = createOpenAI({});

export async function rewrite(message: string): Promise<string> {
  const { text } = await generateText({
    model: openai('gpt-5.5'),
    prompt: `Rewrite this more clearly:\n\n${message}`,
  });

  return text;
}
```

This example does not pass `apiKey` or `baseURL`. In local development, `@ai-sdk/openai` reads `OPENAI_API_KEY` and `OPENAI_BASE_URL` from the `agentuity dev` process env.

## Deployed Apps

For deployed apps, choose one of these paths:

| Path | Use When |
|------|----------|
| set provider keys directly | you need the provider path to be explicit and provider-owned |
| rely on Agentuity gateway env | you have verified the deployed project receives the gateway env needed by your provider SDK |

Local gateway wiring is the default documented path. In deployed apps, set provider keys directly unless you have confirmed the project receives the gateway env needed by your provider SDK.

See [Managing Environment Variables](/deploy-operate/environment-variables): how the CLI finds `AGENTUITY_SDK_KEY` locally and how deploy sync handles `.env` values.
