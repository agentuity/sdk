Use sessions when you need to move from "something failed" to the exact request, log lines, and trace timeline. In v3 framework apps, sessions are platform observability records you inspect through the CLI, Console, or core API helpers rather than a runtime-only `ctx.session` object in every example.

<Callout type="info" title="Existing v2 session APIs still exist">
Existing v2 apps can keep using runtime `ctx.session` and `ctx.thread` patterns. The v3 docs default to framework routes, telemetry packages, and platform inspection APIs.
</Callout>

## Start with the CLI

```bash
agentuity cloud session list --count=25
agentuity cloud session list --success=false
agentuity cloud session get sess_abc123xyz
agentuity cloud session logs sess_abc123xyz
```

`session get` shows request details and a timeline when trace data is available. `session logs` prints collected log entries for that session.

Add `--json` when you want to pipe session output into another tool.

## Filter Sessions

The session list command supports common filters:

| Filter | Example |
|--------|---------|
| project | `agentuity cloud session list --project-id=proj_abc123` |
| deployment | `agentuity cloud session list --deployment-id=deploy_abc123` |
| success | `agentuity cloud session list --success=false` |
| dev mode | `agentuity cloud session list --devmode=false` |
| trigger | `agentuity cloud session list --trigger=api` |
| environment | `agentuity cloud session list --env=production` |
| time window | `agentuity cloud session list --start-after=2026-04-01T00:00:00Z` |

Use `--all` when you want sessions outside the current project context:

```bash
agentuity cloud session list --all --count=50
```

## Programmatic Inspection

Use the CLI for day-to-day debugging. If you are building an internal tool, `@agentuity/core` exports session helpers for platform API access.

```bash
bun add @agentuity/core@alpha @agentuity/telemetry@alpha
```

```typescript
import {
  APIClient,
  sessionGet,
  sessionList,
} from '@agentuity/core';
import { logger } from '@agentuity/telemetry';

const projectId = process.env.AGENTUITY_CLOUD_PROJECT_ID;

if (!projectId) {
  throw new Error('AGENTUITY_CLOUD_PROJECT_ID is required');
}

const catalystUrl =
  process.env.AGENTUITY_CATALYST_URL ?? 'https://catalyst-usc.agentuity.cloud';
const client = new APIClient(catalystUrl, logger);

const failedSessions = await sessionList(client, {
  projectId,
  success: false,
  limit: 10,
});

const firstFailure = failedSessions[0];
const detail = firstFailure
  ? await sessionGet(client, { id: firstFailure.id })
  : null;

logger.info('Failed sessions', failedSessions.map((session) => session.id));
logger.info('First failure detail', detail);
```

`APIClient` reads `AGENTUITY_SDK_KEY` from the environment when you do not pass a key explicitly. Keep that key server-side.

`sessionList()` supports filters for project, deployment, trigger, environment, dev mode, success, time range, thread ID, agent identifier, and metadata.

## Add Useful Context to Logs

Session records tell you when and where a request ran. Your logs should add the application context you will search for later.

```typescript
import { logger } from '@agentuity/telemetry';

interface SupportRequest {
  readonly ticketId: string;
  readonly customerId: string;
  readonly priority: 'low' | 'normal' | 'high';
}

export function logSupportRequest(request: SupportRequest): void {
  logger.child({
    ticketId: request.ticketId,
    customerId: request.customerId,
    priority: request.priority,
  }).info('Support request accepted');
}
```

Prefer opaque internal IDs over raw emails, names, tokens, prompts, or full request bodies. Metadata returned on session records is unencrypted and should follow the same rule.

## Debugging Flow

1. List recent failures with `agentuity cloud session list --success=false`.
2. Open one record with `agentuity cloud session get <session-id>`.
3. Read logs with `agentuity cloud session logs <session-id>`.
4. Use the timeline to find slow spans or failed operations.

<Callout type="tip" title="Use deployment logs for process output">
Session logs are request-scoped. Use `agentuity cloud deployment logs <deployment-id>` when you need deployment-level process logs.
</Callout>
